# Changelog

All notable changes to this project are documented here. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project intends to follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Before 1.0.0, any release may contain breaking changes.

## [Unreleased]

### Added

- User programs get floating point and SIMD (#74, D-016): `cargo xtask` builds them for `x86_64-unknown-linux-gnu` as `no_std` static programs (hardware floats, SSE2) in `target/user/`, with flags only it sets, and checks each with `pharos-elf`; `pharos-user` supplies `memcpy`, `memmove`, `memset`, `memcmp`, `bcmp`, and `rust_eh_personality`. The kernel enables x87 and SSE (and AVX with `XSAVE` when present), keeps a 1 KiB save area per thread, and saves and restores it eagerly on every switch (`kernel/src/arch/x86_64/fpu.rs`); the boot log names the mode. First third-party crate: `libm` 0.2.16 (MIT, no dependencies) in user programs only; NOTICE carries its license. New program `vecprobe`, test kernels `vector_state` (`FXSAVE`) and `vector_state_avx` (`-cpu max`), a floating-point checksum that matches the host. The x87 check in `hardening` now expects the instruction to run.
- M3.0 design (#73), approved by the maintainer: `docs/architecture/user-environment.md` (user programs built for `x86_64-unknown-linux-gnu` by `cargo xtask` only, eager per-thread vector state, system calls 19–23 for memory, sleep, and shared memory, the page limit in `spawn`, a size-class allocator, timeout arguments and error 12 `TIMED_OUT`, `libm`) and storage.md part 8 (the writable store's format, commit order, storage service and its six operations, and crash tests). The threat model gains planned M3.0 rows.
- D-017 accepted (#72): a new `pharos-store` crate with copy-on-write and two superblock roots (live data never overwritten; fallback to the previous generation), whole-file objects and append-only streams, flushes between data, index, and superblock, SHA-256-chained audit records, a storage service in the virtio-blk driver's process with namespace-badged clients, a second writable QEMU disk, and shared-memory capabilities (`mem_share`, `mem_map_cap`) for bulk data such as model files.
- D-016 accepted (#71): user programs are built for `x86_64-unknown-linux-gnu` as `no_std` static programs, since SSE flags have no effect on `x86_64-unknown-none` while `soft-float` is forced and disabling it is being phased out; vector state saved eagerly per thread (`XSAVE` with AVX, else `FXSAVE`; no lazy switching, after LazyFP); `mem_map`/`mem_unmap` with a per-process limit set at `spawn` and a size-class allocator; a microsecond timeout argument on `receive`, `call`, and `irq_wait` with `TIMED_OUT` and `sleep`; math functions from `libm` (MIT) in user space.
- M3.1 (requirements and inference-runtime evaluation) is done: D-010 accepted, CI green on `main`. M3.0 (platform prerequisites for hosting agents) is current. `pharos info` shows the new stage.
- D-010 accepted (#70): Pharos runs our own `no_std` inference engine; GGUF with Q8_0 weights; Qwen2.5-0.5B-Instruct q8_0 (Apache-2.0) for scenario S1; llama.cpp as a host-only reference; deterministic output required. D-011 requirements part accepted: CPU only, SSE2 required with AVX2 used when present, 1 GiB for the inference service and 2 GiB guest memory, no threads. The roadmap records the M3.0 targets, and the threat model the model-file mitigations.
- The M3.1 runtime evaluation is complete (#69): license review of llama.cpp, llama2.c, and the candidate models (Qwen2.5 ships Apache-2.0 texts), and candle dropped with the maintainer's agreement (its examples need system OpenSSL headers, and on Pharos it would need a full standard library).
- The native engine spike runs Qwen2 models from GGUF files with Q8_0 weights (#69): a checked, zero-copy GGUF reader, half-precision and Q8_0 arithmetic, and llama.cpp's Qwen2 graph; prompts come as token IDs. On Qwen2.5-0.5B-Instruct q8_0 its output is identical to llama.cpp's under one of llama.cpp's two attention settings for each of four prompts, and it generates 13.7–14.6 tokens/s on one thread (llama.cpp: 22–23). Its token-by-token prompt processing (14 tokens/s) misses the S1 first-token target; batched prompts are M3.2 work. 24 host tests; the benchmark harness reads build b11609's timing lines and can select prompts.
- Native inference engine spike (#69): new crate `crates/pharos-infer` (`no_std` with `alloc`, no dependencies, `unsafe` forbidden; builds for `x86_64-unknown-none`) runs llama2.c-format Llama models with greedy decoding, following `run.c`, with math functions supplied by the caller; checked, fuzzed parsers; 11 host tests, five mutations caught. `pharos-infer` runs it on the host and prints the benchmark harness's timing line. New `docs/project/inference-evaluation.md` (in progress): pinned engines and models with licenses and checksums, the maintainer's setup steps, and the first findings (the bare-metal target has no SSE, so M3.0 needs an SSE2 user target).
- Inference benchmark harness (#68): `scripts/bench-inference.py` (Python standard library only) runs an engine's command-line tool on the host with fixed prompts (including the S1 summary), seed, and threads, and records load time, prompt and generation tokens per second, peak memory, the generated text and its hash, the model's hash, and the host. Parsers for llama.cpp's timing lines and the native engine's JSON line. It installs and downloads nothing. Host tests run in `check.sh` and CI.
- D-020 accepted (#67): one codebase of `no_std` crates, unit-tested and fuzzed on the Linux host and run unchanged on Pharos, with no throwaway Linux prototype; runtime measurements and output comparison on the host; enforcement counts as done only when a QEMU test on Pharos shows it. Each Phase 3 milestone in the roadmap now says where it runs.
- Phase 3 requirements (`docs/project/phase3-requirements.md`, #66), approved by the maintainer: reference hardware, three use cases, the first agent scenario (summarize a granted file, with seven required failure tests), model needs and candidate sizes, a speed target of 5 tokens/s with the first token within 10 s (binding after #69), SSE2 baseline with optional AVX2, and provisional M3.0 targets.

### Changed

- The IPC round trip is over D-004's 2 µs budget: 2.10–2.19 µs under KVM (found while measuring #74; the vector-state switch adds no measurable time). Recorded in syscalls-ipc.md for a follow-up.
- Roadmap: Phase 3 gains M3.0 (platform prerequisites for hosting agents: SIMD state, user memory, timeouts, writable storage) and M3.8 (a permission-aware knowledge service with provenance). M3.1–M3.5 and M3.7 are refined for durable tasks, a protected audit trail, an emergency stop that needs no agent, per-group budgets with reserved resources, and agent groups after single agents. M4.1 notes what `init` already delivers; M4.3 adds signed updates and rollback. The control-plane/execution-plane rule is stated in the Phase 3 ordering notes. New decision stubs: D-016, D-017, D-019, D-020 (open) and D-018 (proposed: authority only from capabilities, identity for attribution, a trusted path for human control).
- D-010 and D-011 context: a native `no_std` Rust inference engine on Pharos is the leading option to test, with existing engines on the host behind the same interface; Pharos is expected to be CPU-only, with the GPU used for host measurements. Model training stays out of Phase 3.

## [0.2.0] - 2026-10-29

Phase 2 (Core System) is complete. Pharos OS boots in QEMU (UEFI and BIOS) as a capability-based microkernel with isolated user processes, IPC, a read-only filesystem, user-space drivers, a service manager, and a user-space network service. Experimental: QEMU only; see the threat model for the open limits (no IOMMU, no KPTI, one CPU).

The security review was approved by the maintainer. Phase 3 (M3.1) is current. `pharos info` shows the new stage and lists services and networking as implemented. The workspace version is 0.2.0.

The threat model is updated for Phase 2 and lists the open limits carried into Phases 3 and 4.

Requests use the new `call` system call (18); replies use the new non-blocking `send` (flag bit 0, error `WOULD_BLOCK` 11). `init` starts it at boot (the boot now has 2 services). New program `netclient` and test kernel `network`. Task kernel stacks grow from 16 to 32 KiB (D-013 amended): debug builds of `call` overflowed 16 KiB.
- The virtio-net driver (#62): `pharos_programs::virtio_net` (VERSION_1 and MAC only, 16 receive and 16 transmit buffers of 2 KiB, host-tested checks of every used element), on a virtio transport split out of the block driver (`virtio::Transport`, `virtio::Queue`). System call `irq_notify` (17) delivers an interrupt as an endpoint notification bit. Every QEMU run now attaches one modern virtio-net card on slirp user-mode networking. New program `netprobe` and test kernel `virtio_net`: ARP with the slirp gateway and a ping it answers.
- `init`, the service manager (#61): the main kernel now enables preemption and starts `bin/init` with the debug console, the root filesystem, a report endpoint, and the supported devices. `init` starts the services in its compiled-in table in order, each with only its listed capabilities, waits for each (a one-shot exits 0, a daemon reports ready), reports every start, success, failure, skip, missing program, and missing device, and sends the kernel a summary. The boot reports `PHAROS: boot ok` only if every service succeeded (today the virtio-blk driver). New programs `init` and `svc`, test kernel `services`, and `ipc::poll` for kernel tasks.
- Processes start processes (#60): system calls `endpoint_create` (14), `spawn` (15: a program file capability and up to 8 narrowed capabilities, the end signalled as an endpoint notification bit), and `process_status` (16), error `BAD_PROGRAM` (10), at most 32 live processes. Capabilities carry 24-bit badges, set once when passed on and delivered with every message (`send` takes a badge in bits 32–55 of its rights argument). Endpoints have a 32-bit notification word that `receive` returns first (bit 16 set, bits 32–63). `pharos-user` gains `endpoint_create`, `spawn`/`Grant`, `process_status`/`Status`, `Received`, and `rights`; its `send` takes a badge. New programs `spawner` and `child`, and test kernel `spawn`.

D-015 amended: badges replace per-client endpoints. The threat model gains planned processes-and-services and networking sections.

The security review was approved by the maintainer. M2.10 (networking and basic system services) is current. `pharos info` shows the new stage and lists user-space drivers as implemented.
- The virtio-blk driver (#56): a user process (`user/programs/src/bin/virtio-blk.rs`) that checks the device, negotiates only `VERSION_1`, sets up one split virtqueue in DMA memory, reads sectors with interrupt-driven completion, checks every used-ring value (host-tested), and mounts the disk's `pharos-fs` image with the kernel's parser. `pharos-programs` gains a library (`pharos_programs::virtio`, shared with `irqprobe`); `pharos-user` gains a 256 KiB bump heap allocator (its `syscall` module, now listed in AGENTS.md for it). New test kernel `virtio_blk`: the driver reports a file from the disk; a crashing driver is killed alone with its device stopped and memory freed; the wrong device is refused. CI and `check.sh` run the library's host tests.
- Device interrupts (#54): `Object::Interrupt` with rights `IRQ` (on the device) and `WAIT`, system calls `irq_create` (12) and `irq_wait` (13). The kernel routes an MSI-X entry to one of vectors 48–63 by writing the table through its own mapping (drivers never map it); the handler counts, sends EOI, and wakes the one waiter. Revoking the device revokes its interrupts; deleting one masks the entry and frees the vector. `Capability::derive_object` now takes the child's rights from the caller. New program `irqprobe` with a minimal virtio-blk queue (`user/programs/src/virtio.rs`) and test kernel `device_irq`.
- Device capabilities (#55): `Object::Device` with rights `MAP` and `CONFIG`, system calls `config_read` (9), `mmio_map` (10), and `dma_alloc` (11), and error `IN_USE` (9). Drivers map only whole pages of their device's memory BARs, never the MSI-X table or PBA, and get at most 64 DMA pages per device. DMA buffers belong to the device handle and are freed only after bus mastering is off; mapped buffers pin the device for the process's lifetime. A `DEVICE` page-table bit keeps `destroy` from freeing device and DMA pages. `pharos-user` gains `Mapped` (bounds-checked volatile access) and wrappers; new program `devprobe` and test kernel `device_caps`.
- PCI discovery (#53): configuration access through ports `0xCF8`/`0xCFC` with BAR probing that restores every register, `pci::enumerate` with host-tested BAR, capability-list (bounded), and MSI-X decoding, and a boot-log line per function. Every QEMU run attaches a read-only virtio-blk disk (`disk.img`, the `fs-good` image) and no network card. New test kernel `pci`.
- Rust user programs (#52): `user/pharos-user` (safe wrappers for every system call, the entry stub, a panic handler; `unsafe` only in its `syscall` module, now listed in AGENTS.md), `user/programs` with `hello`, linked at `USER_BASE`. New crate `crates/pharos-elf` checks static ELF64 programs completely (fuzzed with 100,000 inputs); `process::load_elf` and `spawn_elf` load them page by page from the filesystem. xtask builds the programs into the boot image as `bin/<name>` and a `programs` test image with ten malformed copies. New test kernel `user_elf`. Host checks exclude `pharos-programs`, which is linted for the bare-metal target instead.
- Driver design (`docs/architecture/drivers.md`, #51), approved by the maintainer: Rust user programs and a checked ELF loader, PCI discovery, device, interrupt, MMIO, and DMA capabilities with system calls 9–13 and error `IN_USE`, MSI-X delivery, and the virtio-blk driver subset. The threat model gains a drivers and devices section (planned mitigations and the no-IOMMU limit).
- Accepted decision D-008 (#50): drivers run in user space with device, interrupt, MMIO, and DMA capabilities; virtio-blk is the only M2.9 driver; Rust user programs are loaded from the boot filesystem; PCI through configuration ports and MSI-X interrupts. No IOMMU yet, recorded as a limit.
- File capabilities (#48): kernel objects `Filesystem` and `File`, a `READ` right, `Capability::derive_object`, and the system calls `open` (7) and `read` (8) with error `NOT_FOUND` (8). Paths and buffers go through the M2.7 user-copy checks; file capabilities pass over IPC and are revoked through the filesystem capability that opened them. New test kernel `files`.
- Kernel filesystem (#47): `fs::mount` mounts a boot module with the shared parser, and the kernel mounts `root` at boot (a bad or missing image is logged, and the kernel keeps running). xtask builds a good test image and 12 corrupted ones, one per check. New test kernel `fs`: files read back, and each corrupted image is rejected with its exact error.
- Read-only RAM disks from Limine modules (#46): the module request, `storage::record_modules` (copies module records before bootloader memory is reclaimed) and `storage::ram_disk`, whose slice `mm::raw::module_bytes` gives only for ranges inside "executable and modules" memory. The boot image carries `kernel/root/` as the filesystem module `root`; test images carry `pattern` and `odd`. New test kernel `ramdisk`. The boot log reports the RAM disk.
- Filesystem image format version 1 (#45): new crate `crates/pharos-fs` (`no_std`, no dependencies, `unsafe` forbidden) with a reproducible builder, a parser that checks the header, directory, paths, ranges, and every CRC-32 before use, and a `BlockDevice` trait; `cargo xtask fs build <dir> <image>` and `cargo xtask fs ls <image>`. Tested with one case per corruption type and 100,000 mutated images.
- Storage design (`docs/architecture/storage.md`, #44), approved by the maintainer: block-device trait, read-only image format version 1 with CRC-32 checksums, validation order, kernel interface, file capabilities with `open` and `read` system calls, and the host tool. The threat model lists storage images as untrusted input.
- Accepted decision D-007 (#43): M2.8 storage is a read-only RAM disk loaded as a Limine module, in a small custom format with CRC-32 checksums, parsed by one safe `no_std` crate shared by the kernel and the host tool. Processes reach files only through capabilities; writes will use copy-on-write.
- M2.7 security review (`docs/security/review-m2.7-kernel-user-boundary.md`, #42) of the kernel/user boundary, covering every system call, user-memory path, entry path, and `unsafe` block added in M2.7. Fixes from it:
  - interrupt entry clears AC, and debug builds assert DF and AC are clear (F1);
  - the kernel's process logs keep their newest 64 entries (F2);
  - `CR0.EM` keeps processes off the x87 FPU and MMX, whose state is not saved per process (F3).
  - New test kernel `hardening` (12 checks), each fix checked to fail without it.
  - The threat model moves the kernel/user boundary into the current scope. The debugging guide shows a verified GDB session that follows a system call back into ring 3.
- IPC (D-014, #41).
  - Synchronous endpoints (`ipc`, with host-tested queues) and the system calls `send`, `receive`, and `revoke`.
  - `sched::block_current` and `sched::wake` let a thread wait without polling.
  - Capabilities gain endpoint objects, derivation (passing with `GRANT`, rights narrowed by a mask), and revocation through the derivation tree, checked on every lookup.
  - Global kernel pages (`CR4.PGE`).
  - Process exits record their time. `IrqMutex` is a plain spin lock in host tests.
  - New test kernel `ipc` (34 checks). It was checked to fail when revocation marks nothing, when derivation keeps all rights, or when `receive` skips its buffer check.
  - Round trip under KVM, release build: 1.97–2.00 µs, which meets the D-004 budget of 2 µs with no margin.
- System calls (D-014, #40).
  - The `syscall`/`sysret` entry (`arch::x86_64::syscall`) runs on the thread's kernel stack with interrupts disabled. Its return address is checked before `sysret`, with an `iretq` fallback, and process address spaces refuse the last user page (CVE-2012-0217).
  - `syscall::decode` performs the stateless checks and is fuzzed on the host. The handler checks capabilities in the per-process `cap::CapTable`, and `AddressSpace::read_user`/`write_user` copy through the direct map after checking range, presence, and access.
  - Calls: `exit`, `yield`, `debug_write` (needs a debug-console capability with `WRITE`), and `delete`, with documented error codes.
  - `process::start` takes the initial capabilities.
  - New test kernel `syscalls` (28 checks), also passing with SMEP/SMAP and under KVM. It was checked to fail when `rdi` is not restored, when rights are ignored, or when the last user page can be mapped.
- User code in ring 3 (#39).
  - The GDT gains user data and code segments in `sysret` order, and every task switch loads TSS `rsp0` with the thread's kernel stack.
  - `context::enter_user` enters ring 3 with every other register cleared and interrupts on.
  - `process::load`, `start`, and `spawn` run a flat binary at `0x400000` with a 64 KiB stack.
  - A CPU exception in user mode kills only that process (`idt::set_user_fault_handler`, `process::init`).
  - SMEP/SMAP are enabled where the CPU has them. `AddressSpace::map_new_page` maps a fresh page with given contents.
  - Test programs live in `arch::x86_64::user_programs`, because `global_asm!` counts as `unsafe`.
  - New test kernel `user_mode` (15 checks), checked to fail without `rsp0`, without the user-fault handler, with interrupts off in user mode, or with kernel pages user-accessible. All test kernels also passed locally with SMEP/SMAP on (`-cpu max`).
- Process address spaces (#38).
  - `AddressSpace::new_user` shares the kernel half, and the kernel pre-creates every kernel-half PML4 table at boot (1 MiB) so the shared entries never change.
  - Page mappings gain a user flag (`Flags::USER_DATA` and `Flags::USER_CODE`, with W^X), and `MapError::WrongHalf` keeps processes out of the kernel half and user pages out of the kernel space.
  - `destroy` frees a process space's pages, tables, and root.
  - `sched::spawn_in` runs a task in a process space: the context owns the space, CR3 switches with the task, and the space is freed when the task is reaped.
  - New test kernel `address_spaces` (15 checks), checked to fail without the CR3 switch, without freeing pages, without the wrong-half check, or without the pre-created tables.
- System-call and IPC design (`docs/architecture/syscalls-ipc.md`, #37), approved by the maintainer, and accepted decision D-014.
  - Processes with one thread each, an address-space layout with W^X, and `syscall`/`sysret` with register arguments.
  - The kernel never dereferences user addresses: it copies through the direct map after validating each buffer. SMEP/SMAP are enabled where available.
  - Capability tables with endpoint and debug-console objects, delegation with `GRANT`, and revocation through a derivation tree.
  - Synchronous IPC endpoints with 256-byte messages and one capability per message.
  - Seven system calls with error codes, and test programs as `global_asm!` flat binaries.
  - The threat model gains a kernel/user boundary section, including the `sysret` non-canonical-address hazard.
- Accepted D-004 as final and recorded the D-012 direction (#36).
  - D-004: the kernel is a capability-based microkernel, with `unsafe` confined to a small hardware layer. It keeps only address spaces, threads and scheduling, IPC, capabilities, interrupt delivery, the timer, the interrupt controller, and the debug console. The IPC budget, measured under KVM with a release build: a message round trip of at most 2 µs and a 1 MiB shared-memory grant of at most 100 µs.
  - D-012 direction: the kernel enforces capabilities (per-process handle tables, rights, passing capabilities over IPC with a grant right, revocation by the original holder) and user space decides policy. The final decision is due at M3.4.
  - A ring 3 prototype measured a `syscall`/`sysret` round trip of 18–21 ns and `int 0x80` at 138 ns under KVM. It confirmed that user code reading kernel memory faults, and that QEMU's default CPU under TCG has no SMEP or SMAP.
- M2.6 complete: the scheduling tests pass in CI ([run 40530704211](https://github.com/codeaiforge/pharos-os/actions/runs/40530704211), 16 test kernels), and a scheduler with preemption removed failed CI ([run 40532363163](https://github.com/codeaiforge/pharos-os/actions/runs/40532363163)). The roadmap marks M2.6 Done and M2.7 Current. `pharos info` reports the new stage and lists the timer and preemptive scheduling as implemented. The architecture overview describes the kernel as of M2.6. The threat model covers starvation, per-task stack overflow, and corrupted task state.
- Preemptive scheduling (D-013, #34).
  - `sched::enable_preemption` creates an idle task, installs the scheduler as the local APIC tick handler (new `apic::set_tick_handler`, called after EOI), starts the 100 Hz tick, and enables interrupts. Each tick wakes due sleepers and switches to the next ready task from inside the interrupt handler (one-tick slice).
  - `sched::sleep` (whole ticks plus one; a host-tested `SleepQueue`) and `sched::set_trace` for serial tracing of switches (debugging guide).
  - `time::start_tick` now reports whether the timer was calibrated.
  - New test kernel `preemption` (12 checks): sleepers wake in deadline order, and a task spinning forever cannot starve the others. It passed with every host core busy and was checked to fail with unsorted sleepers or no time slice.
- Kernel tasks and cooperative switching (D-013, #33).
  - `sched` provides `init`, `spawn(closure)`, `yield_now`, and `exit`, with a round-robin `RunQueue` that is host-tested and generic over the thread type.
  - `arch::x86_64::context` gives each task a 16 KiB stack with a 16 KiB unmapped guard area (window at `0xffffc80000000000`, up to 64 stacks). It switches tasks with a `global_asm!` routine behind a safe `switch`, which checks its preconditions at run time.
  - Exited tasks are freed by the next scheduling call.
  - `IrqMutex` now counts held guards, and switching while one is held panics.
  - New test kernels `tasks` (18 checks) and `task_overflow` (5), checked to fail when a register is lost in the switch, the guard area is mapped, or exited tasks are not freed.
  - New design document `docs/architecture/scheduling.md`.
- Timer calibration and a kernel clock (D-006 timer part, #32). The new `time` module calibrates the local APIC timer and the TSC against polled PIT channel 2, taking the smallest of five 10 ms runs, and rejects implausible rates with a boot error. It also provides `time::uptime()` (from the TSC), `time::delay()`, and `time::start_tick()` (100 Hz). PIT and TSC helpers live in the hardware layer. `kmain` prints a `timer:` line (UEFI and BIOS). The new `timer` test kernel (9 checks) passed with every host core busy and was checked to fail with a wrong tick period or TSC rate. Host unit tests cover the calibration logic.
- Accepted the timer part of D-006 and decision D-013 (scheduling model), #31. Timer: the local APIC timer ticks at 100 Hz, calibrated at boot against PIT channel 2 (the smallest of five 10 ms runs), and uptime comes from the TSC. Scheduler: preemptive round-robin on one CPU with a 10 ms slice; kernel threads run on 16 KiB stacks with guard pages; tasks switch through a `global_asm!` routine, also from inside the timer interrupt; no lock may be held across a switch. A prototype under QEMU TCG showed calibration within 1% when the host is idle. With the host loaded, single runs read up to 29% high, and at 1000 Hz ticks were lost.
- Debugging guide: inspecting the kernel's page tables with GDB and QEMU's monitor (`info mem`, raw entries through the direct map), verified on a test kernel. The threat model covers allocator bugs.
- Kernel heap and `alloc` (D-005, #29): a fixed 4 MiB window at `0xffffc00000000000` backed by fresh frames, allocated by the shared bitmap allocator over 16-byte units (`mm::heap`, safe and host-tested) through a `#[global_allocator]` in `mm::raw` that holds an interrupt-safe lock. `kmain` sets it up after reclaim and runs a smoke test. Allocation failure reaches the panic handler. Test kernels can expect a panic with `testing::set_panic_hook`. New test kernels `heap` (13 checks) and `heap_oom` (3), verified to fail when alignment is ignored.
- Reclaiming bootloader memory (D-005, #28): the memory map is copied into kernel memory, the frame allocator holds bootloader-reclaimable regions reserved from the start, and `mm::reclaim_bootloader_memory` frees them once the kernel's own page tables are active, after retiring Limine's responses (`response()` returns `None` afterwards). `kmain` reclaims as its last step (41 MiB under UEFI in QEMU). New test kernel `reclaim` (12 checks), verified to fail if the responses are not retired.
- The kernel's own page tables (D-005, #27): `arch::x86_64::paging` with an `AddressSpace` (map, unmap, translate; 4 KiB and 2 MiB pages) and a kernel address space with the direct map at Limine's offset, per-segment permissions (text read+execute, rodata read-only, data no-execute, no writable alias of the kernel image), and unmapped guard pages below both kernel stacks; the double-fault stack moved to its own linker segment. `kmain` switches CR3 to it, and the local APIC now maps through it (the M2.4 stopgap is gone). New Limine executable-address request. New test kernels `paging` (20 checks), `write_protect` (4), and `no_execute` (5); `apic_timer` and `double_fault` now run on the kernel's own tables. Each new check was verified to fail when its property is broken. New design document `docs/architecture/memory.md`.
- Physical frame allocator (D-005, #26): `mm::bitmap` (range allocator shared with the future heap) and `mm::frame` (one bitmap per usable region at or above 1 MiB), both safe and host-tested; `mm::raw` adds `IrqMutex` and the direct-map bitmap storage. `kmain` prints the free frame count. New test kernel `frames` (19 checks), verified to fail if the bitmap storage is not reserved.
- Accepted decision D-005 (memory management): one bitmap per memory region for frames, the kernel's own 4-level page tables with an address-space object, Limine's direct-map offset kept with 2 MiB pages, per-section permissions and guard pages for both kernel stacks, reclaim after copying Limine responses, and an own bitmap heap (4 MiB, no crate). `unsafe` is also allowed in a new `mm::raw` module (AGENTS.md updated). Prototype evidence: fragmented memory maps (up to 32 entries), no 1 GiB pages in QEMU's default CPU, and allocation failure reaching the panic handler.
- `cargo xtask run --kernel <ELF>` boots a given kernel, for example a test kernel, so it can be debugged with GDB at source level. The debugging guide now covers exception reports, a verified GDB session on the page-fault path, and diagnosing triple faults with `-d int,cpu_reset`. The threat model notes the kernel's fault handling.
- Local APIC timer interrupts (D-006, #23): `arch::x86_64::apic` maps the APIC register page uncached into Limine's page tables using page-table pages reserved in the kernel image, enables the APIC, and runs its periodic timer on vector 32 with a spurious vector of 255; the legacy PICs stay masked. `kmain` sets up the APIC and prints its ID and version (checked under UEFI and BIOS). New test kernel `apic_timer` (5 checks; also run once by hand under BIOS), verified to hang and fail without EOI. New design document `docs/architecture/interrupts.md`.
- Double faults run on their own stack (TSS IST1), and the kernel runs on a 64 KiB kernel stack with an unmapped guard page below it (#22). `kmain` and test kernels leave Limine's boot stack first. A stack overflow is now reported as a double fault instead of a triple-fault reboot. New test kernel `double_fault` (5 checks), verified to fail without the IST stack or without the guard gap.
- IDT and CPU exception handlers (#21): `global_asm!` entry stubs for vectors 0–31 (stable Rust, minimum version unchanged) and one Rust dispatcher. Breakpoints are reported and execution continues; other exceptions print the vector, decoded error code, CR2, and registers, then fail the run. Test kernels can install a fatal hook; `TestRun` handles now share one count. New test kernel `exceptions` (8 checks) and host unit tests for gates, frame layout, and reports.
- The kernel loads its own GDT (null, kernel code, kernel data, TSS) and TSS at the start of `kmain` (#20), so it no longer depends on Limine's GDT in reclaimable memory. The TSS provides a 16 KiB double-fault stack (IST1, no guard page until M2.5). New test kernel `gdt` (9 checks) and host unit tests for descriptor encoding. `unsafe` is now allowed in submodules of `arch::x86_64` too (AGENTS.md updated).
- Accepted decision D-006 (controller part): local APIC in xAPIC mode, with the local APIC timer as the first hardware interrupt; the legacy PICs stay masked; M2.4 maps the APIC register page into Limine's page tables until M2.5. Prototypes showed that QEMU under TCG cannot provide x2APIC and that PIC interrupts cannot get past Limine's masked LINT0. The timer choice stays open until M2.6.
- Interrupt-safe kernel console (#19): `interrupts_enabled`, `enable_interrupts`, `disable_interrupts`, and `without_interrupts` in the hardware layer; `kprint!`/`kprintln!` hold the console lock with interrupts disabled and restore the previous state. Fatal exception handlers will use the panic handler's print path. New test kernel `interrupt_state` (9 checks).
- Kernel tests inside QEMU (D-009): test kernels in `kernel/tests/` (first: `boot_info`, 9 checks), the `test_kernel!` and `limine_requests!` macros, and `TestRun`. `cargo xtask runner` boots each test kernel under UEFI as Cargo's runner; `cargo xtask test` runs them after the boot check, so CI runs them too. Kernel Clippy now covers test kernels.
- Kernel logging: `kprint!` and `kprintln!` write to one COM1 console behind a new `SpinLock` (no `unsafe`, unit-tested with threads). The panic handler releases the lock first, so a panic during printing is still reported. Not interrupt-safe yet (M2.4).
- CI `qemu` job (Ubuntu 24.04): installs QEMU, OVMF, and xorriso on the runner, runs `cargo xtask test` (boot check under UEFI and BIOS), and checks that two image builds are byte-identical. No new actions, no artifacts. Verified on GitHub: passes on `main` (44 s) with the same image hash as a local build, and fails on a kernel that reports a boot failure.
- `cargo xtask test [--timeout <SECS>]`: headless boot check under UEFI and BIOS. A boot passes only with QEMU exit status 33 and the `PHAROS: boot ok` line within the limit (60 s by default); hung boots are stopped. Serial logs go to `target/xtask/logs/`, and their end is printed on failure.
- Accepted decision D-009 (QEMU automation): pass = QEMU status 33 and a serial marker, 60-second timeout, logs printed on failure, boot check on UEFI and BIOS, test kernels on stable Rust through Cargo's runner and `cargo xtask test`, ISO reproducibility check in CI. Prototyped before acceptance.
- `cargo xtask run [--bios] [--gdb]`: builds the kernel and image and boots it in QEMU (OVMF or SeaBIOS) with serial on the terminal; succeeds only when the kernel signals success (QEMU exit status 33). `--gdb` waits for GDB on `localhost:1234`.
- The kernel signals success or failure (boot errors, panics) through QEMU's `isa-debug-exit` device, only when CPUID reports a hypervisor.
- GDB workflow for breaking into the kernel, verified and documented in `docs/development/debugging.md`.
- Minimal `no_std` kernel (`pharos-kernel`): Limine boots it on UEFI and BIOS (verified in QEMU with `cargo xtask run`, including from a clean checkout); it checks base revision 6, reads the memory map, direct-map offset, bootloader info, and firmware type, reports them on COM1, and halts. Limine protocol structures are written in the project; all hardware `unsafe` code is in `arch::x86_64`.
- Kernel lint rules: `unsafe` denied except in the hardware layer and the Limine protocol module; every `unsafe` block needs a `// SAFETY:` comment (Clippy `undocumented_unsafe_blocks`).
- `cargo xtask` build tool (`xtask/`, no third-party crates): `build` compiles the kernel for `x86_64-unknown-none`; `image` downloads the pinned Limine 12.9.4 release, verifies its SHA-256, and assembles a reproducible hybrid BIOS/UEFI ISO that includes Limine's license notice.
- `scripts/check.sh`: runs the same checks as CI's `check` job, in order.
- Initial direction for D-004: capability-based microkernel with `unsafe` confined to a small hardware layer, plus constraints on early kernel code. Final decision due before M2.7.
- Boot design (`docs/architecture/boot.md`): accepted boot flow, Limine entry contract, image layout, and `xtask` build plan. Nothing boots on `main` yet.
- Accepted decisions D-001 (Limine, own protocol structures), D-002 (UEFI primary, BIOS secondary), and D-003 (`x86_64-unknown-none` on stable, linker script, `xtask`, ISO images, kernel as workspace member).
- Boot evaluation for D-001 to D-003 (`docs/architecture/boot-evaluation.md`), with proposed recommendations: Limine, UEFI primary with BIOS secondary, `x86_64-unknown-none` with an `xtask` build tool. Not accepted yet.
- Prototype evidence for D-001 to D-003 in the boot evaluation: Limine booted a prototype kernel under UEFI and BIOS in QEMU, with reproducible kernel and ISO builds.

### Security

- M2.9 security review (#57, `docs/security/review-m2.9-drivers.md`), four findings fixed: memory BARs that overlap the boot memory map are ignored, so a hostile device cannot get RAM mapped or have the kernel write MSI-X entries into it (F1); a device is granted to one driver at a time, and register mappings pin it like DMA buffers (F2); at most 4 interrupt vectors per device (F3); at most 256 register pages per process (F4). The threat model's drivers section is updated.
- Fixed a stale-TLB bug from #38: unmapping a kernel page (such as a freed task stack) while a process address space was active did not flush the TLB, so the freed frame could stay reachable. Unmapping from the kernel space now always flushes. A new `address_spaces` check fails without the fix.
- Pin `actions/checkout` in CI to the signed v5.1.0 release commit SHA instead of the movable `v5` tag.
