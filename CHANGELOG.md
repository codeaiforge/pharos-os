- Large mappings freed and shared without holding the CPU (#122, resources.md): `mem_unmap`, `mem_share`, and `mem_map_cap` work in batches of 64 pages with interrupts let in between, as `mem_map` does. A 64 MiB process ending had held a trusted task 60–74 ms under TCG. The `exhaustion` kernel (now 1 GiB) has `memprobe` (argument 4) map and unmap 64 MiB, share 128 MiB and map the share, and map 64 MiB more, then stops it, all under the measurement: at most 21–30 ms late, 20 ms of it the timeout's own. Six mutations caught: no pauses while an ending process frees its space (49.6 ms late), in `mem_unmap` (109 ms), in a shared object's free (133 ms), in `mem_share` (69 ms), and in `mem_map_cap` (60 ms), and no revocation check in `mem_map_cap` (`shared_memory`). Freeing the whole space in one pass (no 4-table batches) passes at this size.

Agents started in the services class pass here (the kernel's task is above both) and are caught by `agents`.
- Adversarial tests (#110, capabilities.md "The sandbox"): new test kernel `hostile`, whose agent tries other handles and every other use of its one capability, memory over its limit, ungranted network and inference, control and `trust` requests (answering its own approval request among them), malformed fields, file names reaching outside its own files, a log line faking `trust`'s prompt, a buffer it revokes under the runtime, a full approval queue, and a flood; each is refused (listed in testing.md), while a `keeper` task beside it completes. The runtime now records an agent's refused requests once per kind per attempt (malformed or out of bounds, no grant, not for agents, not askable) with its first example, and the attempt's total when it ends, so a flood cannot fill the trail; the runner checks these records. Nine mutations caught. Docs: the sandbox list no longer says agents cannot create endpoints (they can; their own reach nothing).
- Default-deny networking for agents, with per-destination grants (#109, capabilities.md): a manifest may list UDP destinations (`net = 10.0.2.2:47000`, at most 4, each in its policy entry's new `net`), and a policy entry may list destinations to ask for (`ask_net`). Agents send with `SEND_TO` and read replies with `RECEIVE_FROM` (`agents` 14 and 15) through the runtime's own port (handle 9, port 40100); each send needs the grant and its audit intent (`net send`), and replies are kept only for agents that sent to their source and delivered only while the grant holds, so `revoke <agent> net <a.b.c.d>:<port>` ends them at once. The network service now checks destinations for every client: `init`'s table lists them per network capability and sends them with the new `ALLOW` (5, only without a badge) whenever the service is ready; anything else is `NO_ACCESS`, and a client with no list sends nowhere. New `POLL` (6) returns a waiting datagram without deferring. New test kernel `agents_net`; the `network` kernel checks the refusals. Changed: the manifest key `net` is required (empty for none); the `network` test's refused client has a badge over 16 bits, since badge 0 is now `init`'s.
- Every grant, revocation, and consequential action audited (#108, capabilities.md): the agent runtime (audit client 3) records each attempt's grants and gives none whose record fails, gives an approval only once it is recorded, and records revocations, expiries, and refusals; inference, `DATA_PUT`, `SUBMIT`, and `CANCEL` are an `INTENT` stored before acting and an `OUTCOME` after, and are refused with the new status `NO_AUDIT` when the trail cannot record them. `trust` (client 2) records the user's stops, revocations, and answers; `init` (no badge, which the audit service takes as client 1) records each service start. The shared agent test setup now starts `audit`. The `permissions` kernel kills the audit service and checks `NO_AUDIT`, and the runner reconstructs a task from the trail; the boot check finds a start record for every service. Fixed on the way: a `call` sends its request from the reply buffer, so that buffer must hold the request; seven mutations caught.
- The audit service (#107, capabilities.md): `bin/audit`, the only writer of the audit trail, in the new store namespace `audit` (6). Clients `APPEND` entries (`pharos_proto::audit`: kind, the intent an outcome refers to, actor, task and attempt, action, permission, service, outcome, detail); the service adds the sequence number, the time, and the client's badge, and appends to one stream per boot, `log/<boot>`, which the store chains with SHA-256. An entry the store does not take answers `UNWRITABLE`. `HEAD` gives the boot, record count, and chain head, which `trust` shows at start and on the new `audit` command as the anchor. `init` starts it after the store and before `trust`. New `cargo xtask store audit <image>` checks every chain, sequence numbers, and the boot record, and prints the records. New `audit` test kernel with a tiny store, a killed and restarted service, and the runner checking the anchor against the image; five mutations caught.
- Approval on the trusted path (#106, capabilities.md): an agent may `ASK` for a permission its policy entry lists as askable (new fields `ask_models` and `ask_data`), for some milliseconds or the rest of the task. The runtime asks `trust` with structured fields (`APPROVE`), and `trust` writes the prompt itself: `approve #<n>: <agent> task <id> wants <permission> for this task? (yes <n> / no <n>)`. The user answers `yes <n>` or `no <n>`. The runtime decides every outcome, including no answer within 60 s, and `trust` shows it (`RESOLVED`); at most 4 requests wait, a refusal holds for the task, and `trust` unreachable means no. The `permissions` kernel answers yes, no, and nothing; five mutations caught. The `agents` kernel now sees four accepted manifests; `trust`'s console lines may be 192 bytes.
- Agent permissions revoked while the agent runs (#105, capabilities.md): each task attempt gets grants from its manifest within the policy entry (`pharos_programs::grants`), checked on every request that needs one; `pharos_proto::permission` gives them a wire and a typed form (`model <n>`, `data read`, `data write`, `net <a.b.c.d>:<port>`). New manifest key `data` (`none`, `read`, `write`) and policy field; new runtime operations `DATA_PUT` and `DATA_GET` for the agent's own files (`data/<agent>/<name>`, up to 64 KiB). On the trusted console, `revoke <agent> <permission>` takes a permission from every running task of that agent, for the rest of the task, even across a restart; an inference session on a revoked model is ended. `trust` sends `REVOKE` on a capability the runtime gives it at start (`CHANNEL`), never waiting more than 2 s, and shows the runtime's `REVOKED` answer. New `permissions` test kernel with a trusted-console script; five mutations caught. The `agents` kernel now sees three accepted manifests.
- Revocation unmaps memory at once (#104, capabilities.md): revoking a `Memory` or device capability turns every mapping made through it or a capability derived from it, in every process, into fresh zeroed pages the process owns, with the same access, before `revoke` returns; a revoked device is stopped first (memory decoding, bus mastering, and MSI-X off), and its DMA frames stay allocated until its handle is dropped. A process never faults because another revoked memory it was using, so an agent cannot crash the runtime by revoking a shared buffer. Mappings now record the capability they were mapped through, and the scheduler keeps a task registry to reach another process's address space. `shared_memory` and `device_caps` test it; four mutations caught. Closes the M2.9 and M3.0 revocation limits.
- M3.4 design approved (#103): [capabilities.md](docs/architecture/capabilities.md). Agent permissions (`model`, `data`, `net`) are runtime grants per task attempt, from what the policy entry gives, plus what it lists as askable once the user approves on the trusted console; each may expire and can be revoked while the agent runs. Revoking a memory or device capability turns every mapping made through it into private zeroed pages. Agents reach the network only to granted destinations, checked again by the network service. A new `audit` service writes `INTENT` and `OUTCOME` records around every consequential action, which is refused with `NO_AUDIT` when they cannot be stored; the trusted console shows the chain head as its anchor. Threat model and roadmap updated; agents.md marked implemented.
- Usage reporting (#119, resources.md): `usage` on the trusted console shows the runtime's CPU time and pages (from `trust`'s own capability on it), then each running attempt's CPU time, pages, tokens, datagrams, bytes, and requests, and each group's running attempts, pages, and tokens and bytes this minute, which the runtime sends `trust` as numbers (new `agents` request `USAGE` 22, only from `trust`; `trust` operations `USED` 7 and `GROUP_USED` 8). The runtime records each attempt's usage in the audit trail as it ends (new action `usage` 14). The `budgets` kernel's runner types `usage` and checks the trail; the `hostile` agent's `USAGE` is refused.
- Inference admission (#118, D-022, resources.md): the inference service's new `LIMIT` (6), accepted only without a badge, sets a client's tokens a minute and longest prompt; a `GENERATE` past either is refused with the new `OVER_LIMIT` after tokenizing and before the prompt is processed. The agent runtime gives back tokens an agent was charged but did not use: the prompt's bytes beyond its tokens at once, and the new tokens not generated from the session's record when it ends. The `inference` kernel limits a client through `inferclient` mode 5; the `budgets` kernel's `spender` checks the refunds.
- One agent can no longer hold the runtime for the others (#117, D-022, resources.md): after one call to a service (store, inference, audit, network) times out, the service is stalled and agent requests that need it are answered `BUSY` at once (`NO_AUDIT` for the audit trail), with one 50 ms `INFO` a second that ends the stall when answered; a policy entry's budget has a request `rate` a second, past which a request is held and answered when the rate allows (one more meanwhile is `BUSY`); an agent may have one approval request waiting. New test kernel `fairness`, which stops the network service under the runtime; the `permissions` kernel checks inference is refused at once once the killed audit service has stalled. Changed: the `hostile` agent's second to fifth approval requests are now refused while its first waits, and the runner expects one prompt and one request ended with the task.
- Agent budgets and groups in the runtime (#116, D-022, resources.md): a policy entry's new `budget` (`pharos_proto::manifest::Budget`: `cpu_ms`, `tokens`, `net_sends`, `net_bytes` per attempt, `data_kb` for the agent's files, and its `group`) and the runtime's group table (`Group`: attempts and pages running at once, tokens and network bytes per minute). An inference, `DATA_PUT`, or `SEND_TO` past the agent's or group's budget is refused with the new common status `OVER_LIMIT` (10) before anything is recorded or sent; an attempt over `cpu_ms` (read with `process_usage` at least every 100 ms) is stopped as a failed attempt (`over cpu`); an attempt that does not fit its group waits to start. Each limit reached is recorded once per attempt. `pharos_programs::budgets` holds the logic, host-tested. New test kernel `budgets` with the runtime's policy table 2; `testagent`'s `generate` waits while another agent's session holds the inference service.
- Limits carved from the creator's (#115, D-022, resources.md): a child's pages, live descendants (bits 40–47 of `spawn`'s last argument), and handles with its descendants' (bits 48–59; 0 means 64, one full table) come out of its creator's and return when it ends; asking for more than is left is `TOO_LARGE`, and the creator's own table shrinks to what it has not given away. The kernel gives each process it starts 31 processes and 2,048 handles; `init` gives the agent runtime 16 processes and 320 handles, and the runtime each agent 16 handles and none. `mem_share` charges one page per 512 shared pages for the kernel's bookkeeping, and `mem_map` zeroes large mappings in batches of 64 pages with interrupts on between them. `pharos_user::Limits` replaces `spawn_with`'s separate arguments. Changed: a process can no longer give a child its whole limit while it maps anything itself; `init`'s limit is 3 GiB (was 1.5 GiB), since its services' 2 GiB and more now come out of it; `shmprobe`'s sharer needs 3 pages. Ten mutations caught. The capability table now keeps its count instead of counting its slots on every insert: with the limit check, counting cost the IPC round trip about 60 ns (2,058 and 2,052 ns). Measured against #114's kernel alternately (9 runs each), medians 2,012 and 1,935 ns against 1,995 and 2,000 ns: no difference beyond the host's spread, but this host now runs near D-004's 2,000 ns budget.
- Scheduling classes and CPU time (#114, D-022, resources.md): three classes, trusted (kernel tasks, `init`, `trust`), services (every other service), and agents, each its own round robin, a higher class always first; a wake-up of a higher class switches at once at the end of the system call or device interrupt instead of at the next tick. `spawn` takes the child's class in bits 32–33 of its last argument (`pharos_user::spawn_with`, `Class`), refusing a class above the caller's with `TOO_LARGE`; `init` starts `trust` in its own class and the other services below it, and the agent runtime starts agents in the agents class. Each task's CPU time is counted in TSC cycles at every switch (one `rdtsc`, a plain load and store), kept in the process record when it ends, and read with the new system call 26 `process_usage` (CPU time in microseconds, pages mapped, live descendants; needs `WAIT`). New test kernel `classes`; the `spawn`, `services`, and `agents` kernels check the class rules and `process_usage`; fourteen mutations caught. IPC round trip under KVM: medians 1,915 and 1,959 ns (9 runs each), within D-004's budget.
- M3.5 design approved (#113): [resources.md](docs/architecture/resources.md). Three scheduling classes (trusted, services, agents), a woken higher-class task preempting at once; CPU time counted per process with one `rdtsc` per switch (measured within D-004's IPC budget) and a new `process_usage` call; pages, processes, and handles carved from the creator's at `spawn`; `mem_map` zeroing in batches with interrupts on; per-attempt budgets in the policy entry (`cpu_ms`, `tokens`, `net_sends`, `net_bytes`, `rate`) plus `data_kb` and named groups, with the new common status `OVER_LIMIT`; a stalled service answered at once with `BUSY`, requests over the rate held, one approval place per agent; inference admission per client with `LIMIT`; a `usage` command on the trusted console and usage records in the audit trail.
- The knowledge service (#143, knowledge.md): `bin/knowledge`, in new store namespace `knowledge` (8), with its interface in `pharos_proto::knowledge` (`PUT`, `GET`, `HISTORY`, `QUERY`, `VERIFY` from `trust` only, `ATTACH`, `INFO`) and its logic in `pharos_programs::knowledge::Service`. Scopes are a fixed table (`notes`, `ops`, `hr`, `team`, `test`), named by number in requests, with the caller's readable scopes as a bit each; bulk data goes through the caller's buffer, copied out before it is read. Puts come only from the runtime's badge, never as the user or from the host; anything whose scope or evidence the reader cannot reach answers as if it did not exist. New test kernel `knowledge` (versions put, corrected, in conflict, retracted, hidden by evidence, queried, and verified; everything survives a restart); four mutations caught, each by both the host tests and the kernel.
- The knowledge data model (#142, knowledge.md): `pharos_proto::knowledge`, the version record (format 1: scope, key, number, `claim` or `retraction`, the version it replaces, author, source, time, SHA-256, up to 4 tags, 4 evidence references, and 8 evidence scopes, and up to 4 KiB of content) and the user's mark; `pharos_programs::knowledge::Index`, which rebuilds every version and mark from the store (`<scope>/<key>/v<n>` and `m<n>`, each written once) and derives each version's status: superseded, retracted, stale through its evidence, verified only by a mark with its hash, and conflicting heads. Writes are planned against it (the version they replace, evidence that exists and the writer can read, at most 256 keys a scope, 64 versions a key, 8 evidence scopes), and queries leave out what the reader, or the evidence chain, cannot reach. Host-tested and fuzzed; ten mutations caught.
- M3.8 design approved (#141): [knowledge.md](docs/architecture/knowledge.md). One immutable store file per version in new namespace `knowledge` (8), with provenance set by the service from who sent it; conflicting, superseded, retracted, stale (through evidence), and verified status derived, never stored; queries that leave out anything whose scope or evidence chain the caller cannot read; permissions `knowledge read <scope>` and `knowledge write <scope>` (wire kinds 7 and 8); runtime requests `KNOWLEDGE_PUT`, `KNOWLEDGE_GET`, `KNOWLEDGE_HISTORY`, `KNOWLEDGE_QUERY`, and `PROMOTE` (28–32), each put audited as new action `knowledge` (18); `verify <scope> <key> <version> <hash>` on the trusted console, with the first 8 hexadecimal digits of the content's SHA-256; `MAX_SPAWN_CAPS` to be raised from 8 to 12.

### Fixed

- A knowledge writer could replace or retract a version it cannot read (M3.8 review F1, #147): `Index::plan` checked only that the replaced version exists, so in the `poison` kernel `gullible` could correct `ops/pay`, which cites `hr`, and learn it exists. A version the writer cannot read is now as missing as one that does not exist (`REPLACES`); `knowledge write` without `read` adds new keys only. Host test `what_the_caller_cannot_read_does_not_exist` and the `poison` kernel check it
- A stored knowledge version could be rewritten (M3.8 review F2, #147): when the store kept a version but its answer was lost, the next put of that key wrote the same `v<n>` over it. The service now reads the path first and indexes a valid version it finds there instead of writing; host test `a_stored_version_whose_answer_was_lost_is_kept`
- The IPC round trip back within D-004's 2 µs budget (#121): M3.5 had added about 30–60 ns, to medians of 1,973–2,043 ns. `sched::current_id` (called on every system call through `process::current`) is now a plain load of the running task's ID, kept at each switch, and `sched::stopping` (also on every system call) is a plain load while no task is told to end, instead of each taking the scheduler's lock. Median 1,935 ns under KVM (1,889–1,990 ns over 5 runs); alternating with the kernel before, 1,895 against 2,024 ns.
- A stale pause mark (M3.5 review F1, #121): `process::with_pauses` restored the mark it found, so two tasks' overlapping pauses could leave a live task marked outside it, and a later drop of a shared object by that task could let interrupts in where its caller relied on them staying off. Each task now clears only its own mark. The review is [review-m3.5-resources.md](docs/security/review-m3.5-resources.md), approved by the maintainer on 2026-11-05: two new `unsafe` blocks, both in the hardware layer; IPC round trip re-measured under KVM: 1,973 to 2,043 ns, over D-004's budget, before the fix above. M3.5 closed after the CI gate (removing the runtime's per-attempt token check failed CI on a throwaway branch); M3.6 is current, and `pharos info` says so.
- `mem_map_cap` could leave a mapping a revocation had missed (#122): with pauses between its batches, a capability revoked during the call was swept before the mapping was recorded, so the mapping kept showing the object. It now checks the capability once mapped and answers `REVOKED`. The `shared_memory` kernel revokes a capability while `memprobe` (argument 5) maps it and checks the pages read zeros or the call was refused; it fails without the check.
- A process stopped during one of `mem_map`'s pauses between batches was ended by the tick right there, in the middle of the call, so what the call held, its process among it, was never dropped, and with it every capability the process held (since #120 made the pauses let interrupts in). The tick handler is now told whether it interrupted user mode (`apic::set_tick_handler` takes `fn(bool)`) and ends a process only then; the call sees the stop and ends it on its way out. The `user_memory` kernel stops a `memprobe` holding an endpoint while it maps 64 MiB and checks the endpoint is released; it fails without the fix.
- `mem_map`'s pause between batches let no interrupt in (#120): it ran `sti` then `cli`, and `sti` takes effect only after the next instruction, so a large mapping held the CPU for its whole zeroing after all (#115 said otherwise), and a woken higher-class task waited for the whole call: loading the test model held a trusted task 33–41 ms, and a 64 MiB mapping 106–146 ms. The pause is now `sti; nop; cli` (`arch::x86_64::interrupt_window`), so a tick or device interrupt there switches to a woken task. The `exhaustion` kernel fails without it.
- `RECEIVE_FROM` without a `net` grant (M3.4 review F1, #111): any agent could make the runtime poll the network service, blocking it up to 1 s each time that service was stalled. It now answers `NO_ACCESS` without a grant, and polls only for an agent that has sent somewhere; the `hostile` agent checks it.
- A lost wakeup in kernel-side IPC (M3.4 review F2, #111): `ipc::send`, `call`, and `receive` could block a kernel thread forever if it was preempted between queueing and blocking; this hung the `trust` test kernel once in CI. They now run with interrupts off; system calls, which already do, use `send_now`, `call_now`, and `receive_now`. The review is [review-m3.4-permissions.md](docs/security/review-m3.4-permissions.md), approved by the maintainer on 2026-11-04: no new `unsafe` in M3.4; IPC round trip re-measured under KVM, median 1,963 ns, within D-004's budget. M3.4 closed after the CI gate (removing the runtime's `SEND_TO` grant check failed CI on a throwaway branch); M3.5 is current, and `pharos info` says so.
- The emergency stop by name missed processes (M3.3 review, F1): `trust`'s `stop <agent>` stopped only the first process registered under the name, so a second task of the same agent kept running. It now stops every process registered under the name. The `trust` test registers two `worker` agents and checks `stop worker` stops both while the runtime still runs. The review is [review-m3.3-agents.md](docs/security/review-m3.3-agents.md), approved by the maintainer on 2026-11-03: no new `unsafe` in M3.3; IPC round trip re-measured under KVM, median 1989 ns, within D-004's budget. M3.3 closed after the CI gate (a `BEGIN` that stopped recording its key failed CI on a throwaway branch); M3.4 is current, and `pharos info` says so.
- One inference client could erase another's `RESULT` record (M3.2 review, F1): the service kept only the last ended session's record, and any client's next `GENERATE` cleared it. Records are now kept per client until that client's next session ends. The `inference` test checks a record survives a second client's session (mutation-checked).
- Batched prompts were slow on Pharos (#90): the 32 tokens' quantized inputs were separate vectors, which Pharos's allocator aligns to 4 KiB, so the same block of each fell in the same L1 cache set. They are now one vector. The S1 prompt on Pharos went from 12.8–13.4 s to 6.3–6.4 s, and on the host from 8.4–9.0 s to 6.1 s. Output is bit-identical (same SHA-256 as in M3.1).

  - Round trip under KVM, release build: 1.97–2.00 µs, which meets the D-004 budget of 2 µs with no margin.
- System calls (D-014, #40).
  - The `syscall`/`sysret` entry (`arch::x86_64::syscall`) runs on the thread's kernel stack with interrupts disabled. Its return address is checked before `sysret`, with an `iretq` fallback, and process address spaces refuse the last user page (CVE-2012-0217).
  - `syscall::decode` performs the stateless checks and is fuzzed on the host. The handler checks capabilities in the per-process `cap::CapTable`, and `AddressSpace::read_user`/`write_user` copy through the direct map after checking range, presence, and access.
  - Calls: `exit`, `yield`, `debug_write` (needs a debug-console capability with `WRITE`), and `delete`, with documented error codes.
  - `process::start` takes the initial capabilities.
  - New test kernel `syscalls` (28 checks), also passing with SMEP/SMAP and under KVM. It was checked to fail when `rdi` is not restored, when rights are ignored, or when the last user page can be mapped.
- User code in ring 3 (#39).
  - The GDT gains user data and code segments in `sysret` order, and every task switch loads TSS `rsp0` with the thread's kernel stack.
  - `context::enter_user` enters ring 3 with every other register cleared and interrupts on.
  - `process::load`, `start`, and `spawn` run a flat binary at `0x400000` with a 64 KiB stack.
  - A CPU exception in user mode kills only that process (`idt::set_user_fault_handler`, `process::init`).
  - SMEP/SMAP are enabled where the CPU has them. `AddressSpace::map_new_page` maps a fresh page with given contents.
  - Test programs live in `arch::x86_64::user_programs`, because `global_asm!` counts as `unsafe`.
  - New test kernel `user_mode` (15 checks), checked to fail without `rsp0`, without the user-fault handler, with interrupts off in user mode, or with kernel pages user-accessible. All test kernels also passed locally with SMEP/SMAP on (`-cpu max`).
- Process address spaces (#38).
  - `AddressSpace::new_user` shares the kernel half, and the kernel pre-creates every kernel-half PML4 table at boot (1 MiB) so the shared entries never change.
  - Page mappings gain a user flag (`Flags::USER_DATA` and `Flags::USER_CODE`, with W^X), and `MapError::WrongHalf` keeps processes out of the kernel half and user pages out of the kernel space.
  - `destroy` frees a process space's pages, tables, and root.
  - `sched::spawn_in` runs a task in a process space: the context owns the space, CR3 switches with the task, and the space is freed when the task is reaped.
  - New test kernel `address_spaces` (15 checks), checked to fail without the CR3 switch, without freeing pages, without the wrong-half check, or without the pre-created tables.
- System-call and IPC design (`docs/architecture/syscalls-ipc.md`, #37), approved by the maintainer, and accepted decision D-014.
  - Processes with one thread each, an address-space layout with W^X, and `syscall`/`sysret` with register arguments.
  - The kernel never dereferences user addresses: it copies through the direct map after validating each buffer. SMEP/SMAP are enabled where available.
  - Capability tables with endpoint and debug-console objects, delegation with `GRANT`, and revocation through a derivation tree.
  - Synchronous IPC endpoints with 256-byte messages and one capability per message.
  - Seven system calls with error codes, and test programs as `global_asm!` flat binaries.
  - The threat model gains a kernel/user boundary section, including the `sysret` non-canonical-address hazard.
- Accepted D-004 as final and recorded the D-012 direction (#36).
  - D-004: the kernel is a capability-based microkernel, with `unsafe` confined to a small hardware layer. It keeps only address spaces, threads and scheduling, IPC, capabilities, interrupt delivery, the timer, the interrupt controller, and the debug console. The IPC budget, measured under KVM with a release build: a message round trip of at most 2 µs and a 1 MiB shared-memory grant of at most 100 µs.
  - D-012 direction: the kernel enforces capabilities (per-process handle tables, rights, passing capabilities over IPC with a grant right, revocation by the original holder) and user space decides policy. The final decision is due at M3.4.
  - A ring 3 prototype measured a `syscall`/`sysret` round trip of 18–21 ns and `int 0x80` at 138 ns under KVM. It confirmed that user code reading kernel memory faults, and that QEMU's default CPU under TCG has no SMEP or SMAP.
- M2.6 complete: the scheduling tests pass in CI ([run 40530704211](https://github.com/codeaiforge/pharos-os/actions/runs/40530704211), 16 test kernels), and a scheduler with preemption removed failed CI ([run 40532363163](https://github.com/codeaiforge/pharos-os/actions/runs/40532363163)). The roadmap marks M2.6 Done and M2.7 Current. `pharos info` reports the new stage and lists the timer and preemptive scheduling as implemented. The architecture overview describes the kernel as of M2.6. The threat model covers starvation, per-task stack overflow, and corrupted task state.
- Preemptive scheduling (D-013, #34).
  - `sched::enable_preemption` creates an idle task, installs the scheduler as the local APIC tick handler (new `apic::set_tick_handler`, called after EOI), starts the 100 Hz tick, and enables interrupts. Each tick wakes due sleepers and switches to the next ready task from inside the interrupt handler (one-tick slice).
  - `sched::sleep` (whole ticks plus one; a host-tested `SleepQueue`) and `sched::set_trace` for serial tracing of switches (debugging guide).
  - `time::start_tick` now reports whether the timer was calibrated.
  - New test kernel `preemption` (12 checks): sleepers wake in deadline order, and a task spinning forever cannot starve the others. It passed with every host core busy and was checked to fail with unsorted sleepers or no time slice.
- Kernel tasks and cooperative switching (D-013, #33).
  - `sched` provides `init`, `spawn(closure)`, `yield_now`, and `exit`, with a round-robin `RunQueue` that is host-tested and generic over the thread type.
  - `arch::x86_64::context` gives each task a 16 KiB stack with a 16 KiB unmapped guard area (window at `0xffffc80000000000`, up to 64 stacks). It switches tasks with a `global_asm!` routine behind a safe `switch`, which checks its preconditions at run time.
  - Exited tasks are freed by the next scheduling call.
  - `IrqMutex` now counts held guards, and switching while one is held panics.
  - New test kernels `tasks` (18 checks) and `task_overflow` (5), checked to fail when a register is lost in the switch, the guard area is mapped, or exited tasks are not freed.
  - New design document `docs/architecture/scheduling.md`.
- Timer calibration and a kernel clock (D-006 timer part, #32). The new `time` module calibrates the local APIC timer and the TSC against polled PIT channel 2, taking the smallest of five 10 ms runs, and rejects implausible rates with a boot error. It also provides `time::uptime()` (from the TSC), `time::delay()`, and `time::start_tick()` (100 Hz). PIT and TSC helpers live in the hardware layer. `kmain` prints a `timer:` line (UEFI and BIOS). The new `timer` test kernel (9 checks) passed with every host core busy and was checked to fail with a wrong tick period or TSC rate. Host unit tests cover the calibration logic.
- Accepted the timer part of D-006 and decision D-013 (scheduling model), #31. Timer: the local APIC timer ticks at 100 Hz, calibrated at boot against PIT channel 2 (the smallest of five 10 ms runs), and uptime comes from the TSC. Scheduler: preemptive round-robin on one CPU with a 10 ms slice; kernel threads run on 16 KiB stacks with guard pages; tasks switch through a `global_asm!` routine, also from inside the timer interrupt; no lock may be held across a switch. A prototype under QEMU TCG showed calibration within 1% when the host is idle. With the host loaded, single runs read up to 29% high, and at 1000 Hz ticks were lost.
- Debugging guide: inspecting the kernel's page tables with GDB and QEMU's monitor (`info mem`, raw entries through the direct map), verified on a test kernel. The threat model covers allocator bugs.
- Kernel heap and `alloc` (D-005, #29): a fixed 4 MiB window at `0xffffc00000000000` backed by fresh frames, allocated by the shared bitmap allocator over 16-byte units (`mm::heap`, safe and host-tested) through a `#[global_allocator]` in `mm::raw` that holds an interrupt-safe lock. `kmain` sets it up after reclaim and runs a smoke test. Allocation failure reaches the panic handler. Test kernels can expect a panic with `testing::set_panic_hook`. New test kernels `heap` (13 checks) and `heap_oom` (3), verified to fail when alignment is ignored.
- Reclaiming bootloader memory (D-005, #28): the memory map is copied into kernel memory, the frame allocator holds bootloader-reclaimable regions reserved from the start, and `mm::reclaim_bootloader_memory` frees them once the kernel's own page tables are active, after retiring Limine's responses (`response()` returns `None` afterwards). `kmain` reclaims as its last step (41 MiB under UEFI in QEMU). New test kernel `reclaim` (12 checks), verified to fail if the responses are not retired.
- The kernel's own page tables (D-005, #27): `arch::x86_64::paging` with an `AddressSpace` (map, unmap, translate; 4 KiB and 2 MiB pages) and a kernel address space with the direct map at Limine's offset, per-segment permissions (text read+execute, rodata read-only, data no-execute, no writable alias of the kernel image), and unmapped guard pages below both kernel stacks; the double-fault stack moved to its own linker segment. `kmain` switches CR3 to it, and the local APIC now maps through it (the M2.4 stopgap is gone). New Limine executable-address request. New test kernels `paging` (20 checks), `write_protect` (4), and `no_execute` (5); `apic_timer` and `double_fault` now run on the kernel's own tables. Each new check was verified to fail when its property is broken. New design document `docs/architecture/memory.md`.
- Physical frame allocator (D-005, #26): `mm::bitmap` (range allocator shared with the future heap) and `mm::frame` (one bitmap per usable region at or above 1 MiB), both safe and host-tested; `mm::raw` adds `IrqMutex` and the direct-map bitmap storage. `kmain` prints the free frame count. New test kernel `frames` (19 checks), verified to fail if the bitmap storage is not reserved.
- Accepted decision D-005 (memory management): one bitmap per memory region for frames, the kernel's own 4-level page tables with an address-space object, Limine's direct-map offset kept with 2 MiB pages, per-section permissions and guard pages for both kernel stacks, reclaim after copying Limine responses, and an own bitmap heap (4 MiB, no crate). `unsafe` is also allowed in a new `mm::raw` module (AGENTS.md updated). Prototype evidence: fragmented memory maps (up to 32 entries), no 1 GiB pages in QEMU's default CPU, and allocation failure reaching the panic handler.
- `cargo xtask run --kernel <ELF>` boots a given kernel, for example a test kernel, so it can be debugged with GDB at source level. The debugging guide now covers exception reports, a verified GDB session on the page-fault path, and diagnosing triple faults with `-d int,cpu_reset`. The threat model notes the kernel's fault handling.
- Local APIC timer interrupts (D-006, #23): `arch::x86_64::apic` maps the APIC register page uncached into Limine's page tables using page-table pages reserved in the kernel image, enables the APIC, and runs its periodic timer on vector 32 with a spurious vector of 255; the legacy PICs stay masked. `kmain` sets up the APIC and prints its ID and version (checked under UEFI and BIOS). New test kernel `apic_timer` (5 checks; also run once by hand under BIOS), verified to hang and fail without EOI. New design document `docs/architecture/interrupts.md`.
- Double faults run on their own stack (TSS IST1), and the kernel runs on a 64 KiB kernel stack with an unmapped guard page below it (#22). `kmain` and test kernels leave Limine's boot stack first. A stack overflow is now reported as a double fault instead of a triple-fault reboot. New test kernel `double_fault` (5 checks), verified to fail without the IST stack or without the guard gap.
- IDT and CPU exception handlers (#21): `global_asm!` entry stubs for vectors 0–31 (stable Rust, minimum version unchanged) and one Rust dispatcher. Breakpoints are reported and execution continues; other exceptions print the vector, decoded error code, CR2, and registers, then fail the run. Test kernels can install a fatal hook; `TestRun` handles now share one count. New test kernel `exceptions` (8 checks) and host unit tests for gates, frame layout, and reports.
- The kernel loads its own GDT (null, kernel code, kernel data, TSS) and TSS at the start of `kmain` (#20), so it no longer depends on Limine's GDT in reclaimable memory. The TSS provides a 16 KiB double-fault stack (IST1, no guard page until M2.5). New test kernel `gdt` (9 checks) and host unit tests for descriptor encoding. `unsafe` is now allowed in submodules of `arch::x86_64` too (AGENTS.md updated).
- Accepted decision D-006 (controller part): local APIC in xAPIC mode, with the local APIC timer as the first hardware interrupt; the legacy PICs stay masked; M2.4 maps the APIC register page into Limine's page tables until M2.5. Prototypes showed that QEMU under TCG cannot provide x2APIC and that PIC interrupts cannot get past Limine's masked LINT0. The timer choice stays open until M2.6.
- Interrupt-safe kernel console (#19): `interrupts_enabled`, `enable_interrupts`, `disable_interrupts`, and `without_interrupts` in the hardware layer; `kprint!`/`kprintln!` hold the console lock with interrupts disabled and restore the previous state. Fatal exception handlers will use the panic handler's print path. New test kernel `interrupt_state` (9 checks).
- Kernel tests inside QEMU (D-009): test kernels in `kernel/tests/` (first: `boot_info`, 9 checks), the `test_kernel!` and `limine_requests!` macros, and `TestRun`. `cargo xtask runner` boots each test kernel under UEFI as Cargo's runner; `cargo xtask test` runs them after the boot check, so CI runs them too. Kernel Clippy now covers test kernels.
- Kernel logging: `kprint!` and `kprintln!` write to one COM1 console behind a new `SpinLock` (no `unsafe`, unit-tested with threads). The panic handler releases the lock first, so a panic during printing is still reported. Not interrupt-safe yet (M2.4).
- CI `qemu` job (Ubuntu 24.04): installs QEMU, OVMF, and xorriso on the runner, runs `cargo xtask test` (boot check under UEFI and BIOS), and checks that two image builds are byte-identical. No new actions, no artifacts. Verified on GitHub: passes on `main` (44 s) with the same image hash as a local build, and fails on a kernel that reports a boot failure.
- `cargo xtask test [--timeout <SECS>]`: headless boot check under UEFI and BIOS. A boot passes only with QEMU exit status 33 and the `PHAROS: boot ok` line within the limit (60 s by default); hung boots are stopped. Serial logs go to `target/xtask/logs/`, and their end is printed on failure.
- Accepted decision D-009 (QEMU automation): pass = QEMU status 33 and a serial marker, 60-second timeout, logs printed on failure, boot check on UEFI and BIOS, test kernels on stable Rust through Cargo's runner and `cargo xtask test`, ISO reproducibility check in CI. Prototyped before acceptance.
- `cargo xtask run [--bios] [--gdb]`: builds the kernel and image and boots it in QEMU (OVMF or SeaBIOS) with serial on the terminal; succeeds only when the kernel signals success (QEMU exit status 33). `--gdb` waits for GDB on `localhost:1234`.

Limine protocol structures are written in the project; all hardware `unsafe` code is in `arch::x86_64`.

### Security

- M2.9 security review (#57, `docs/security/review-m2.9-drivers.md`), four findings fixed: memory BARs that overlap the boot memory map are ignored, so a hostile device cannot get RAM mapped or have the kernel write MSI-X entries into it (F1); a device is granted to one driver at a time, and register mappings pin it like DMA buffers (F2); at most 4 interrupt vectors per device (F3); at most 256 register pages per process (F4).
