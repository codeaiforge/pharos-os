All tests run on the host:

```sh
cargo test                          # host crates (default members)
cargo test -p pharos-kernel --lib   # kernel library logic
cargo test -p pharos-programs --lib # user-program library (driver logic)
```

## Boot check (QEMU)

```sh
cargo xtask test               # boot check under UEFI and BIOS, headless
cargo xtask test --timeout 120 # longer limit per boot (default 60 s)
cargo xtask test --shard 2/4   # the 2nd of 4 shares of the test kernels only
```

Each boot passes only if QEMU exits with status 33 **and** the serial log contains the line `PHAROS: boot ok`, within the time limit (decision D-009). Since #61 the kernel prints it only after `init` reports that every boot service succeeded (today: the virtio-blk driver mounting the disk), so a broken service fails the boot check. A kernel that reports failure (status 35), exits without signalling, prints a different marker, or hangs fails the check; a hung QEMU is stopped at the limit. Both boots write the same store, so afterwards the command checks its audit trail (#108) as `cargo xtask store audit` does: two streams, each with a `start` record from `init` for every boot service (including those started before the audit service was ready). The command prints one line per firmware and, on failure, the last lines of the serial log. Full logs: `target/xtask/logs/boot-uefi.log` and `boot-bios.log`.

Needs QEMU, OVMF, and xorriso, so it is not part of `scripts/check.sh`. CI runs it in the `qemu` job on every push to `main` and on manual runs (Ubuntu 24.04 runner), followed by a check that two image builds are byte-identical. **Shards (since 2026-11-09):** the `qemu` job runs as 4 parallel jobs, `cargo xtask test --shard N/4`. Each runs its share of the test kernels, split by their CI times (`SHARD_SECONDS` in `xtask`, the slowest first, each to the share with the least time so far; host-tested to cover every kernel once). Share 1 also runs the boot check and the reproducible-image check. Run #236 took 895 s in one job, 813 s of it booting test kernels one after another; the shares hold about 210 s each. A share that fails does not stop the others (`fail-fast: false`). The weights only balance the shares: a kernel missing from the table counts 5 s and still runs. Run #242, the first with shares, took 7 min 12 s (shares 288–423 s): each share compiled for 58–143 s before its first test kernel, so the job caches the Rust build (`target/debug`, `target/x86_64-unknown-none`, `target/user`, the Cargo registry) and the Limine archive with `actions/cache`, keyed by the commit and restoring the newest earlier build, with `CARGO_INCREMENTAL=0`. First runs on 2026-10-27: the job took 44 s (20 s installing packages, boot checks 3.2 s UEFI and 0.4 s BIOS), and the CI image hash matched the local build (`51bc0a7f…`). A branch whose kernel reports a boot failure made the job fail at "Boot check", with the kernel's reason in the job output ([run 40473362173](https://github.com/codeaiforge/pharos-os/actions/runs/40473362173)). After the boot check, `cargo xtask test` runs the kernel tests (next section); CI runs both. For an interactive boot with serial on the terminal, use `cargo xtask run` (see [debugging.md](debugging.md)).

## Kernel tests (QEMU)

Code that needs real hardware state (boot information, CPU, later memory and interrupts) is tested inside QEMU by **test kernels**: small `no_main` kernels in `kernel/tests/`, each booted on its own (decision D-009). `cargo xtask test` runs them after the boot check, through `cargo test -p pharos-kernel --target x86_64-unknown-none --test '*'`; Cargo hands each test binary to `cargo xtask runner`, which boots it headless under UEFI.

Output, for each test kernel:

```text
  PHAROS-TEST: memory map present ... ok
  ...
  PHAROS-TEST: 9 passed, 0 failed
test kernel boot_info (uefi): PASS in 2.2 s
```

A test kernel passes only if it ran at least one check, none failed, and it ended with `PHAROS: tests ok` and QEMU status 33 within the time limit. A failed check, a panic, a hang, or a test kernel with no checks fails the run.

To add a test kernel:

1. Create `kernel/tests/<name>.rs` with `#![no_std]`, `#![no_main]`, `pharos_kernel::test_kernel!(run);`, and `fn run(t: &mut TestRun)` calling `t.check("description", condition)` for each check. The Limine responses are available as `requests::MEMMAP` and so on.
2. Add a `[[test]]` entry with `name = "<name>"` and `harness = false` to `kernel/Cargo.toml`.
3. Run `cargo xtask test`. Each test kernel costs about two seconds under UEFI, so group related checks.

### User programs and drivers

User programs and drivers live in `user/programs` (package `pharos-programs`): one file per program in `src/bin/`, and code they share (the virtio-blk driver core) in the library `src/lib.rs`. They use only `pharos-user`, safe Rust, and `#![no_std]`/`#![no_main]` with `pharos_user::entry!(main)`.

- **Build:** `cargo xtask test`, `run`, and `image` build them for `x86_64-unknown-linux-gnu` as `no_std` static programs (since M3.0, D-016: `CARGO_TARGET_DIR=target/user` and flags only `cargo xtask` sets, [user-environment.md](../architecture/user-environment.md); each result is checked with `pharos-elf`) and put each program listed in `USER_PROGRAMS` (`xtask/src/main.rs`) into the filesystem images as `bin/<name>`: the `root` module of the main kernel and the `programs` module of test kernels. A new program needs an entry in that list.
- **Run:** a test kernel mounts `programs` and starts a program with `process::spawn_elf(&fs, b"bin/<name>", arg, caps)`, giving it exactly the capabilities it needs (handles 1, 2, ... in order). Devices are granted with `DeviceHandle::grant`, which refuses a device that is still granted. The program reports through `debug_write`, and the test kernel reads its lines with `process::debug_output()` and its end with `process::exits()` or `process::kills()`.
- **Devices in QEMU:** every run attaches `disk.img` (the `fs-good` test image) as a modern-only virtio-blk device and one modern-only virtio-net card on slirp user-mode networking, so test kernels always find the same devices.
- **Host endpoint:** `cargo xtask runner` (and so `cargo xtask test` and `cargo test --test <name>`) runs a UDP echo server on `127.0.0.1:47000` while each test kernel boots. slirp forwards the guest's datagrams for `10.0.2.2` to the host's loopback, so the guest reaches it at `10.0.2.2:47000`; nothing else on the host or beyond is used. If the port is taken, the runner stops with a message saying so. `PHAROS_PCAP=1` also records each test kernel's network traffic ([debugging.md](debugging.md#capture-network-traffic)).
- **Host tests:** the library's device-independent logic runs on the host with `cargo test -p pharos-programs --lib`; use it for every check of untrusted device values, because QEMU's device never sends bad ones.
- **Lint:** `env CARGO_TARGET_DIR=target/user RUSTFLAGS="--cfg pharos_user -C panic=abort" cargo clippy -p pharos-programs --target x86_64-unknown-linux-gnu -- -D warnings` (part of `scripts/check.sh`). The separate target directory keeps these flags away from host builds of the same triple.

Debugging a program with GDB: [debugging.md](debugging.md#debug-a-rust-user-program-or-driver).

At the end of M2.8 ([run 40576869275](https://github.com/codeaiforge/pharos-os/actions/runs/40576869275)) it took 249 s with 25 test kernels on a slower runner (about 5.5 s per kernel, the storage kernels `ramdisk`, `fs`, and `files` included); the packages came from the cache, with no download from the mirror. At the end of M2.9 ([run 40713610670](https://github.com/codeaiforge/pharos-os/actions/runs/40713610670)) it took 140 s with 31 test kernels: 9 s for packages from the cache, 120 s for the boot check and the kernels (about 3.9 s each, the driver kernels `device_caps`, `device_irq`, and `virtio_blk` included), and the reproducibility check. At the end of M2.10, which closed Phase 2 ([run 40835736689](https://github.com/codeaiforge/pharos-os/actions/runs/40835736689)), it took 227 s with 34 test kernels: 12 s for packages from the cache, 209 s for the boot check and the kernels (about 4.7 s each, the service and network kernels `spawn`, `services`, `virtio_net`, and `network` included; `network` also exchanges a datagram with the host echo server), and the reproducibility check.


## IPC round trip (KVM)

`cargo xtask bench-ipc [--runs <N>]` measures the IPC round trip against D-004's budget of 2 µs (#81). It builds the release `ipc` test kernel with `PHAROS_IPC_ROUND_TRIPS=100000` (a build-time setting; the test kernel's default is 1,000), boots it N times (default 5) under KVM with `-cpu host`, and prints each run's time per round trip and the median, minimum, and maximum. Each run is ping and pong exchanging 8-byte messages (each `send` then `receive`), averaged over the 100,000 round trips. It needs read-write access to `/dev/kvm` and stops with a message saying so otherwise. CI cannot run it: CI runs QEMU under emulation (TCG), where timing means nothing, so the measurement is a manual step before each milestone gate. Logs go to `target/xtask/runner/bench-ipc/`.

Host noise matters: on the reference host (i9-10900K, `powersave` governor) runs of 15 vary by about 250 ns, so compare medians of 15 or more runs.

## S1 inference (KVM)

`PHAROS_MODEL=<qwen2.5-0.5b-instruct-q8_0.gguf> cargo xtask bench-infer [--runs <N>]` measures scenario S1 on Pharos against its targets (#90). It writes a store holding the model (under its manifest path), the S1 prompt (the `summary` prompt of `scripts/bench-inference.py`; a host test checks they match), and `models/s1.expected`, the text `pharos-infer` generates on the host for it with `libm` (128 tokens, about 15 s, also printed with the host's times). It builds the release `inference` test kernel with `PHAROS_INFER_S1` set, which then runs `inferclient` mode 3 instead of its checks, and boots it N times (default 3) under KVM with `-cpu host` and 2 GiB. Each run prints model load, prompt time, first-token time (the `GENERATE` call plus one token's average), tokens per second, and the service's peak mapped memory; the run fails unless the text equals the host's byte for byte. Then the medians against the targets (first token 10 s, 5 tokens/s), and the first request after boot (load plus first token). About 50 s per run. Like `bench-ipc`, it needs `/dev/kvm` and is a manual step. Logs and the store go to `target/xtask/runner/bench-infer/`. Results: [inference-evaluation.md](../project/inference-evaluation.md).

## Inference benchmarks (host)

`scripts/bench-inference.py` measures an inference engine's command-line tool on the Linux host, for the runtime evaluation in M3.1 (#68, #69). Results are host results (D-020): they say nothing about Pharos until the engine runs there.

- **What it runs:** two fixed prompts (a short one, and the S1 scenario's "summarize this report" with a one-page text written for the harness), each `--runs` times, with seed 42 and the given thread count.
- **What it records**, per run: the engine's load time and prompt and generation tokens per second, the process's wall time and peak resident memory (from `wait4`), the generated text and its SHA-256, the model file's size and SHA-256, the engine version, and the host's CPU, SIMD flags, and memory. It prints medians and whether the output was identical across runs (determinism), and writes JSON to `target/bench/` (never committed).
- **Engines:** `llama` reads llama.cpp's `llama_perf_context_print:` lines (and the older `llama_print_timings:` form); `native` reads one JSON line, `{"load_ms", "prompt_tokens", "prompt_ms", "gen_tokens", "gen_ms"}`, which Pharos's own engine prints last. Other engines get a parser when their real output has been recorded.
- **It installs and downloads nothing.** A missing engine binary or model file stops it with a message naming what is missing.

The engine command follows `--`; `{model}`, `{prompt}`, `{n}`, `{threads}`, and `{seed}` are filled in, and other text (including braces) is passed unchanged. For example, with llama.cpp's `llama-completion` (check the flags against `--help` of your build):

```sh
python3 scripts/bench-inference.py --engine llama --model models/model.gguf \
    --label "model q4_k_m" --threads 1 --runs 3 \
    --version-cmd "llama.cpp/build/bin/llama-completion --version" \
    -- llama.cpp/build/bin/llama-completion -m {model} -p {prompt} -n {n} -t {threads} -s {seed} --temp 0
```

Host tests (`scripts/test_bench_inference.py`, in `check.sh` and CI): parsing of llama.cpp's timing lines in both forms (quoted from llama.cpp's documentation, not recorded here), the native JSON line and malformed ones, placeholder filling, peak memory of a process that allocates 64 MiB, a missing binary or model, a failing engine, and an end-to-end run with a stand-in engine.

## Quality gates

Run `scripts/check.sh` before every pull request. It runs these commands, the same ones as CI's `check` job, and stops at the first failure:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --exclude pharos-kernel --exclude pharos-programs --all-targets --locked -- -D warnings
cargo build --workspace --exclude pharos-kernel --exclude pharos-programs --locked
cargo test --workspace --exclude pharos-kernel --exclude pharos-programs --locked
cargo test -p pharos-kernel --lib --locked
cargo test -p pharos-programs --lib --locked
cargo clippy -p pharos-kernel --target x86_64-unknown-none --lib --bins --test '*' --locked -- -D warnings
env CARGO_TARGET_DIR=target/user RUSTFLAGS="--cfg pharos_user -C panic=abort" cargo clippy -p pharos-programs --target x86_64-unknown-linux-gnu --locked -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --exclude pharos-kernel --exclude pharos-programs --no-deps --locked
RUSTDOCFLAGS="-D warnings" cargo doc -p pharos-kernel --target x86_64-unknown-none --no-deps --locked
python3 scripts/check-links.py
python3 -m unittest -q scripts/test_bench_inference.py
```

Why the split: the kernel targets bare metal (`x86_64-unknown-none`, decision D-003), so it is excluded from host checks and linted for its own target. Its target-independent logic is unit-tested on the host through the library. CI's `msrv` job also builds and tests the host crates and the kernel library on Rust 1.85. `scripts/check.sh` repeats those three commands (`cargo +1.85 build`/`test`) when Rust 1.85 is installed (`rustup toolchain install 1.85 --profile minimal`), and says it skipped them otherwise. Newer language features, such as let chains (Rust 1.88), fail only there: four M2.7 commits passed every local check yet failed CI's `msrv` job for that reason, fixed in #42.

## Writing tests

- Every behavior change comes with a test; every bug fix with a test that fails without the fix.
- Keep tests deterministic: no network beyond the runner's localhost echo server, no wall-clock dependence, no reliance on host state. Pass environment facts in as parameters.
- Test error paths and exit codes, not only the happy path.
- Never report a test as passing unless it ran and passed.
